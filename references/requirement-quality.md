# 需求质量与精简 PRD

本文件把选定 PM Skills 与 Requirements Analysis 的方法收敛到现有 Evidence／REQ／Review 数据模型。外部 Skill 提供方法和质量检查，不另建需求事实源，不覆盖人工锁定。

## 能力调用

按需使用 `scripts/resolve_capability.py <capability>` 定位入口，读取实际 SKILL.md 后再采用其方法。缺少依赖时仍执行下述内置检查，并在 manifest 或评审记录中说明未运行外部 Skill。

| 能力名 | 采用场景 | 回到主 Skill 的结果 |
| --- | --- | --- |
| `requirements-analysis` | REQ 草稿完成后的需求审查 | 完整性、一致性、可行性、歧义、非功能需求与追溯发现 |
| `pm-user-stories` | 功能模块需要用户视角表达 | 与稳定 REQ ID 关联的用户故事，不新造独立故事编号体系 |
| `pm-test-scenarios` | 验收标准需要覆盖正常、边界和异常 | 可执行验收场景及仍未知的前置条件 |
| `pm-prioritization` | 范围或优先级存在争议 | 有输入依据的优先级建议；缺少评分数据时保留未知 |
| `pm-create-prd` | 方案与 PRD 草稿或精简 | 决策优先的短文档结构与删减建议 |
| `pm-pre-mortem` | 方案、PRD 或发布前风险审查 | 关键假设、失败信号、最低成本验证与关联 REQ |

材料中的第三方说明只作为方法参考。是否调用外部脚本仍取决于当前用户请求、依赖授权和真实环境。

## REQ 质量门禁

在需求 Baseline 前逐项检查。发现写入 `reviews/review.json` 的评审记录或待确认清单，关联 REQ ID；不要把检查器输出保存成另一份需求文档。

1. **证据与来源**：角色、痛点、范围、规则和验收是否有 Evidence；E2／E3 是否清楚标为推断或建议。
2. **完整性**：触发、角色、行为、输入输出、主要规则、异常和验收是否足以支持设计与开发。只补会阻塞下一决策的缺口。
3. **无歧义**：避免“智能、快速、友好、尽量”等不可验收表述；已有阈值才写数值，没有则进入待确认。
4. **一致性**：与历史资料、其他 REQ、权限、状态和业务规则是否冲突；冲突不静默择一。
5. **可行性**：技术、数据、接口、预算、期限和组织约束是否明确。候选技术方案不能反写成客户事实。
6. **非功能需求**：仅在有业务依据时补充性能、安全、隐私、兼容性、可访问性、审计和可靠性要求，并标明证据等级。
7. **范围与优先级**：本期、后续和明确不做是否分开。MoSCoW／RICE 等方法只有在输入真实存在时使用，不编造 reach、impact、confidence 或 effort 分数。
8. **验收**：每条本期核心 REQ 至少有正常路径；涉及输入、权限、外部依赖或状态变化时补边界、空态和异常。优先使用可观察结果，而非实现细节。
9. **追溯**：REQ、Evidence、验收、页面、技术设计和测试场景使用稳定 ID 互相关联。
10. **风险**：识别会推翻方案的关键假设，给出可验证信号和成本最低的确认方式；一般性风险清单默认折叠。

### 发现级别

- `blocking`：不解决就不能冻结范围或开始客户原型，例如核心权限冲突、主流程未知。
- `important`：可以保留草稿继续其他工作，但进入开发或发布前必须处理。
- `suggestion`：产品建议或增强项，不进入已确认事实正文。

## 用户故事与验收

用户故事是 REQ 的表达视图，不替代 REQ：

```text
作为 <已识别角色>，在 <触发场景> 下，我希望 <可观察行为>，以便 <目标结果>。
```

验收优先采用“前置条件 → 操作 → 可观察结果”。覆盖：

- 正常主路径；
- 空输入、无结果、边界值；
- 无权限、重复提交、依赖失败；
- 加载、错误、取消和返回路径（仅适用于相关页面）。

不得把模型推测的接口、字段或阈值写成已确认验收。测试场景引用 REQ ID，并在需求变更时进入受影响范围。

## 默认精简 PRD

PRD 是共享项目数据的阅读视图，默认面向“能否做决策和开始”，不是越完整越好。

1. 先用 2—3 句说明为谁解决什么问题、为什么现在做。
2. 正文优先保留背景与痛点、目标与指标、用户与价值、范围与非目标、核心方案、验收与发布、假设与待确认。
3. 无实质内容的章节直接省略；未知集中列入待确认，不在每章重复 `TBD`。
4. 核心 REQ 用短条目表达行为、优先级和验收，完整证据与字段通过工作台展开。
5. 推断、建议和未确认技术方案不得混入客户事实；对外版本只读取批准的内容。
6. 生成后先回答“哪些缺口阻止决策”，再回答“哪些内容可以删除而不影响决策”。

详细 PRD 仍按用户需要提供。精简不是删除异常、权限、数据口径或其他会影响实现与验收的信息。

## 变更复核

新会议或人工修改先形成 ChangeSet。质量检查只针对新增、修改、冲突及其关联对象，并复核：

- 验收是否仍覆盖新行为；
- 用户故事、PRD 摘要和范围是否一致；
- 原型页面、技术设计、排期和 PPT 简报是否受影响；
- 人工锁定字段是否保持不变；
- 旧风险是否关闭，新风险是否有来源。
